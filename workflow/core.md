Workstyle is the selected workflow. Preserve the user's explicit instructions and
the target project's conventions. Use workstyle-task for multi-step implementation,
investigation, scientific work, and task recovery. Keep its record in the target
project's .workstyle/tasks/. Routine questions and tiny edits need no task ledger.
Investigate consequential unknowns with source inspection or a small experiment.
Carry authorized work through implementation, relevant verification, and delivery;
do not stop merely because a plan or first partial result is ready.
Report concrete blockers with evidence, without declaring unverified success.
For meaningful complex changes, use an independent read-only reviewer subagent
when available. Give it requirements and raw artifacts, let it find issues
independently, then verify its findings yourself. Simple edits need no delegation.
For scientific work, distinguish execution success, numerical validity, and the
strength of the conclusion. Preserve the original acceptance criteria.
Show important findings and decisions in chat as well as saving files.
Use teach for requested learning, retro for requested retrospectives, and prototype
when a runnable state/UI prototype can settle a design question. Resolve upstream
tool names to the current CLI's available skill, file, shell and agent tools.
Resolve skill references relative to their SKILL.md; save results in the project.
When switching CLIs, recover progress from project files and task records. Native
chat history belongs to each CLI and may not contain the other CLI's conversation.
DeepWiki supports public-repository investigation; verify important claims against
the actual source/version. Use the isolated browser MCP to verify web behavior.
If an optional MCP is unavailable, continue with available tools and state the
verification gap. MCP connectivity alone is not task acceptance.
