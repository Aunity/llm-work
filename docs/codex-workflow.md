# Codex 使用方法与任务完成质量

Codex 的质量取决于模型、任务定义、可获取的证据、执行环境和验证循环。复杂任务可保留较高推理强度，进一步把精力投入到调查、实验、独立审查和可恢复的任务状态。

资料核对日期：2026 年 11 月 16 日。本文面向 Codex CLI；App、IDE 和托管执行环境的能力与权限应分别核实。

## 定义完成质量

| 维度 | 评估问题 |
| --- | --- |
| 需求符合度 | 是否解决原始问题，是否遗漏约束和边界情况 |
| 正确性 | 实际行为、数据和推导是否支持结论 |
| 验证力度 | 是否运行相关检查，是否检查真实产物 |
| 完整交付 | 是否完成实现、验证、说明与必要的后续处理 |
| 可复现性 | 是否保留输入、环境、参数、命令和证据 |
| 学习迁移 | 使用者能否解释关键决策，并完成类似问题 |

对于科研任务，否定假设、确认方法不可行或识别数据不足，都可能构成有效交付。完成条件不应迫使代理追求正面结果。

## 调查未知并验证关键假设

在方案阶段区分已确认事实、关键未知和设计取舍。能够用小样例、源码检查或最小实验验证的事项，应尽量获得证据后再决定大规模实现。

OpenAI 的 ExecPlan 实践建议对未知设计先做原型，再推进实现。ExecPlan 是项目约定的计划文档，不是 Codex 内置模式；该文章已归档，适合借鉴方法，模型名与配置需要另查当前资料。[ExecPlans 实践](https://developers.openai.com/cookbook/articles/codex_exec_plans)

## 规划与持续执行

当前官方文档说明，Codex CLI 可使用 `/plan` 调查与设计，使用 `/goal` 围绕持续目标工作。目标应包含结果、约束和验证方法；能否达标仍取决于环境、权限和外部条件。[长期任务说明](https://learn.chatgpt.com/docs/long-running-work)

明确需求后，应给予实现与修复过程足够自主权。缺少关键业务信息、外部授权或不可自行补足的数据时，报告具体阻塞及已有证据。

```text
请完整推进任务，优先保证思考与交付质量。

目标：
背景与关键文件：
约束与已授权范围：
完成条件：

先调查代码和相关资料，验证会影响方案的关键未知。
维护计划、发现、关键决策、失败尝试和验证记录。
根据实际结果修正方案，完成实现和相关验收。
交付时说明结果、证据位置、验证范围和未解决的问题。
```

## 使用评估循环

先明确评估方法，再运行基线、定位失败、做有针对性的修改、重新评估并记录结果。对图片、页面和计算结果，还需要直接检查实际产物。[困难问题迭代指南](https://learn.chatgpt.com/use-cases/iterate-on-difficult-problems)

| 任务 | 合适的证据 |
| --- | --- |
| 修复错误 | 原始问题复现、修复后的行为、相关回归检查 |
| Web App | 浏览器操作、截图、控制台和网络请求 |
| 科研计算 | 基线、对照、数据划分、随机性、数值合理性和结果文件 |
| 文献研究 | 原文位置、检索与筛选记录、引用核验、相反证据 |
| 发布集成 | 实际入口、真实请求、运行日志和输出契约 |

验收口径发生变化时，保留原标准并说明变更原因。针对同一测试集反复优化的结果，不应直接视为泛化能力提高。

## 保持任务状态可恢复

跨会话任务宜保留目标、当前进展、已验证发现、关键决策、失败尝试、证据路径和下一步。任务状态应有一个权威来源，避免多个计划系统分别维护不一致的完成情况。

以下结构是建议，可按项目缩减：

```text
AGENTS.md                 项目入口与运行约定
ARCHITECTURE.md            结构与关键边界
docs/exec-plans/           当前与历史任务计划
docs/decisions/            决策及依据
experiments/              输入、参数、脚本和结果
```

OpenAI 的 harness 实践将简短的 AGENTS.md 用作知识地图，深入说明放在结构化文档中，并将可重复检查的约束落实为工具。[Harness engineering](https://openai.com/index/harness-engineering/)

## 独立调查与审查

主代理负责需求、决策和整合；子代理适合独立调查、测试和审查。各任务应明确输入、范围、产物与证据要求。并行修改代码时划分文件所有权，或使用独立 worktree。[子代理说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

```text
请使用子代理：
一位检查方案中的错误假设和需求遗漏；
一位检查实现、测试与验收的一致性。
审查结论需指向源码、原始资料或可复现步骤。
主代理复核发现、完成修复，再统一交付。
```

不同意见、证据和复现实验有助于减少盲点；多个代理表达一致意见，本身不构成正确性证明。

## CLI 操作

| 操作 | 用途 |
| --- | --- |
| `/status` | 检查当前模型、权限、目录与上下文 |
| `/debug-config` | 检查配置层及生效来源 |
| `/plan` | 调查、设计和明确任务 |
| `/goal` | 持续推进具有明确结束条件的目标 |
| `/diff` 与 `/review` | 查看与审查工作区修改 |
| `/compact` | 压缩会话；关键状态仍应落到任务记录 |
| `codex resume --last` | 恢复最近会话 |
| `codex fork --last` | 从既有会话探索另一条路线 |
| `codex exec` | 将代理接入脚本和结构化交付流程 |

可用命令以本机 `--help` 和交互菜单为准。[官方命令参考](https://learn.chatgpt.com/docs/developer-commands)

## 学习模式

学习任务可以采用预测、尝试、反馈、解释和迁移练习的顺序。要求代理先给出问题与提示，让使用者完成关键判断，再讨论解法。跨天保留概念、错误类型与后续练习，以检验能否独立应用。

## 扩展选择原则

Skills 提供可重复的流程，MCP 或 CLI 提供事实与操作能力。优先选择能补齐实际缺口的扩展，并通过真实任务验证收益。具体候选见 [Skills 与 MCP 候选全景](skills-mcp-landscape.md)，效果评估见 [试用与效果评估](evaluation-plan.md)。
